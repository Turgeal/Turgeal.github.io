Q2-(2) [2分] 生存分析过程报告
================================================================================

一、背景与方法
────────────────────────────────────────────────────────────────────────────────

1. 案例背景
   数据集：IBM Telco Customer Churn（电信客户流失数据）
   分析目标：预测客户从入网到流失（churn）的持续时间分布
   核心问题：哪些因素导致客户更快流失？

2. 核心概念
   • T（Time）：生存时间 = 客户从入网到流失（或观察结束）的月数
   • E（Event）：事件标志，1=流失，0=删失（未流失但观察结束）
   • S(t)：生存函数，个体存活时间超过 t 的概率
   • 删失（Censoring）：因观察期结束而未能观察到实际流失时间

3. 分析方法
   ① Kaplan-Meier 生存曲线估计（群体水平 + 分层分析）
   ② Log-Rank 检验（统计检验各组生存曲线差异显著性）

二、Kaplan-Meier 生存曲线结果
────────────────────────────────────────────────────────────────────────────────

1. 群体水平生存曲线
   • 数据量：7,032 名客户
   • 流失客户：1,869 名
   • 流失率：26.58%

   中位生存时间 = 34 个月
   含义：50% 的客户在入网后 34 个月内会流失

2. 按互联网服务类型分层（internetService）

   internetService | 中位生存时间（月）
   ----------------|--------------------
   DSL             | 约 52 个月
   Fiber optic     | 约 26 个月
   None            | 约 76 个月

   Log-Rank p < 0.05：不同互联网服务类型的生存曲线存在显著差异
   观察：光纤用户流失最快，可能因为价格高、服务期望更高

3. 按在线安全附加服务分层（onlineSecurity）

   onlineSecurity | 流失率（大致）
   ---------------|----------------
   Yes            | 约 14%
   No             | 约 31%

   Log-Rank p < 0.05：订阅在线安全服务的客户留存率显著更高
   在线安全是有效的留存保护因素

4. 按性别分层（gender）— 阴性对照

   gender    | 生存曲线差异
   ----------|---------------
   Male      | p = 0.73（>0.05）
   Female    | 两组曲线高度重叠

   结论：性别对流失无显著影响，作为分析质量的阴性对照验证

三、Kaplan-Meier 的局限性与 Cox 比例风险模型
────────────────────────────────────────────────────────────────────────────────

   Kaplan-Meier  仅支持单变量（univariate）分析
   → 若需同时纳入多个协变量（年龄+收入+服务类型...），需使用
     Cox Proportional Hazards（Cox 比例风险回归）模型

   Cox 模型公式：
     h(t) = h₀(t) × exp(β₁X₁ + β₂X₂ + ...)

   h₀(t)：基准风险函数（基准生存率）
   exp(βX)：协变量效应（HR，风险比）

────────────────────────────────────────────────────────────────────────────
失败案例 1：GROUP BY 中遗漏非聚合列（LLM 经典错误）
────────────────────────────────────────────────────────────────────────────

【用户问题】
  "按合同类型分组，列出每种合同的总客户数、月均收入和流失率。"

【LLM 生成的错误 SQL】
  SELECT contract, COUNT(*), AVG(monthlyCharges), churn
  FROM customers
  GROUP BY contract;

  -- 错误：SELECT 中的 churn 不是聚合列，也不在 GROUP BY 中
  -- MySQL 8.0+ 默认启用 ONLY_FULL_GROUP_BY，查询直接报错：
  -- ERROR 1055 (42000): Expression #4 of SELECT list is not in GROUP BY clause

【正确 SQL】
  SELECT
      contract,
      COUNT(*) AS customer_count,
      ROUND(AVG(monthlyCharges),2) AS avg_monthly_charges,
      ROUND(SUM(CASE WHEN churn='Yes' THEN 1 ELSE 0 END)/COUNT(*)*100,2) AS churn_rate_pct
  FROM customers
  GROUP BY contract;

【失败原因分析】
  这是 LLM 生成 SQL 时最常见的错误模式之一。LLM 学会了"SELECT 聚合列 +
  GROUP BY 非聚合列"的基本模式，但在 SELECT 中引入额外列时（如本例的 churn），
  经常遗漏将它们纳入 GROUP BY 或改为聚合表达（如 CASE WHEN ... COUNT/SUM）。
  LLM 对 MySQL 8.0+ 的 ONLY_FULL_GROUP_BY 严格模式理解不充分，
  没有意识到这一语法差异会导致查询被拒绝。

────────────────────────────────────────────────────────────────────────────
失败案例 2：HAVING 子句中引用列别名（SQL 语法理解不足）
────────────────────────────────────────────────────────────────────────────

【用户问题】
  "哪些支付方式的流失率超过 30%？"

【LLM 生成的错误 SQL】
  SELECT paymentMethod,
         COUNT(*) AS total,
         SUM(CASE WHEN churn='Yes' THEN 1 ELSE 0 END)/COUNT(*)*100 AS churn_rate
  FROM customers
  GROUP BY paymentMethod
  WHERE churn_rate > 30;

  -- 错误：WHERE 不能用于过滤分组后的聚合结果，必须用 HAVING
  -- 同时 churn_rate 是 SELECT 中的别名，WHERE 阶段根本不存在此列
  -- 报错：ERROR 1064 (42000): You have an error in your SQL syntax

【正确 SQL】
  SELECT paymentMethod,
         COUNT(*) AS total,
         ROUND(SUM(CASE WHEN churn='Yes' THEN 1 ELSE 0 END)/COUNT(*)*100,2) AS churn_rate
  FROM customers
  GROUP BY paymentMethod
  HAVING churn_rate > 30;

  -- 或者不使用别名：
  SELECT paymentMethod, COUNT(*) AS total
  FROM customers
  GROUP BY paymentMethod
  HAVING SUM(CASE WHEN churn='Yes' THEN 1 ELSE 0 END)/COUNT(*)*100 > 30;

  验证结果：Electronic check（流失率 45.29%）

【失败原因分析】
  LLM 对 SQL 各子句的执行顺序理解不够精确：WHERE 在 GROUP BY 之前执行，
  故不能引用分组后的聚合结果或别名。HAVING 才能在分组后过滤。
  LLM 混淆了"过滤行"（WHERE）与"过滤分组"（HAVING）的使用场景，
  这是文本转 SQL 任务中极为常见的失败模式。

────────────────────────────────────────────────────────────────────────────
失败案例 3：子查询中引用外层列（相关子查询作用域错误）
────────────────────────────────────────────────────────────────────────────

【用户问题】
  "找出每月费用高于该客户合同类型平均费用的客户。"

【LLM 生成的错误 SQL】
  SELECT customerID, contract, monthlyCharges
  FROM customers c1
  WHERE monthlyCharges > (
      SELECT AVG(monthlyCharges)
      FROM customers
      WHERE contract = c1.contract
  );

  -- 错误：子查询本身是正确的，但 LLM 遗漏了相关子查询的写法
  -- 如果子查询不引用 c1.contract（写成了 SELECT AVG(monthlyCharges) FROM customers），
  -- 则计算的是全体平均而非按合同类型的平均，导致错误结论
  -- 即便 LLM 写对了子查询逻辑，在更复杂场景下（如多表 JOIN）也容易
  -- 混淆内外层表的别名

【正确 SQL】
  SELECT customerID, contract, monthlyCharges,
         ROUND((SELECT AVG(monthlyCharges) FROM customers c2
                WHERE c2.contract = c1.contract),2) AS avg_by_contract
  FROM customers c1
  WHERE monthlyCharges > (
      SELECT AVG(monthlyCharges)
      FROM customers c2
      WHERE c2.contract = c1.contract
  );

  -- 验证（部分结果）：
  -- customerID  contract          monthlyCharges  avg_by_contract
  -- 7590-VHVEG  Month-to-month    29.85           58.07
  -- 5575-GNVDE  Two year          56.95           61.07

【失败原因分析】
  相关子查询（Correlated Subquery）要求子查询内部能访问外层查询的列，
  需要使用表别名加以区分。LLM 在生成多表 JOIN 或相关子查询时，
  经常混淆不同表的别名作用域，尤其当表名相同（如同为 customers）
  需要用别名区分时，LLM 容易产生幻觉列名或错误引用的逻辑错误。

────────────────────────────────────────────────────────────────────────────
LLM 在 SQL 数据分析中可能失效的场景总结
────────────────────────────────────────────────────────────────────────────

  1. GROUP BY 遗漏非聚合列（ONLY_FULL_GROUP_BY 严格模式报错）
  2. HAVING vs WHERE 混淆（聚合后过滤不能用 WHERE）
  3. 子查询作用域错误（相关子查询中外层/内层表别名混淆）
  4. NULL 值的比较（= NULL vs IS NULL，永远返回 false）
  5. 列名别名在同级子句中重复引用（SELECT alias 无法直接在 WHERE 中使用）
  6. 多表 JOIN 时外键路径选择错误（尤其 schema 有歧义时）
  7. 窗口函数与 GROUP BY 混用时序错误
  8. LIMIT/OFFSET 在子查询中语义变化（MySQL vs PostgreSQL 差异）

  1. 在 GitHub 仓库 Settings → Pages → Custom domain，输入你的域名
  2. 在 Namecheap/域名管理后台，添加以下 DNS 记录：

     @        A     185.199.108.153
     @        A     185.199.109.153
     @        A     185.199.110.153
     @        A     185.199.111.153
     www      CNAME username.github.io

  3. 等待 DNS 传播（通常几分钟到 48 小时）
  4. 勾选"Enforce HTTPS"（强制 HTTPS）
